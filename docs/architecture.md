# DevBox 架构设计

[文档索引](README.md) · [项目规则](../AGENTS.md) · [开发指南](development.md)

本文定义 DevBox 的产品边界、平台模型、领域模型、工具插件、用户目录、持久化、前后端通信、状态同步、异步任务、安全和发布范围。后续实现以本文为唯一架构基线；与具体实现冲突时，先修正设计再改代码。

文档定位：DevBox 唯一架构基线。当前版本提供环境查询、`.devbox` 目录初始化、uv、Python、Node.js、npm、pnpm、Git、Bash 与 Zsh 系统检测、托管清单扫描、工具快照缓存、下载代理设置和对应前端页面；安装、任务、事件、完整持久化和多平台能力按本文的交付顺序实现。

当前注册的 Tauri command 为 `get_environment`、`list_tools`、`refresh_tools`、`get_settings`、`update_settings` 和 `test_proxy`。命令表中的其他能力随对应业务模块一起交付。

## 目标与边界

DevBox 是跨平台开发工具链管理器，负责检测、安装、切换、更新和回滚开发工具版本。首期目标工具包括 uv、Python、Node.js 和 Git。

DevBox 不负责项目依赖管理。`pip`、`npm`、项目虚拟环境和 lockfile 仍由对应工具处理。

产品遵守以下边界：

- 所有操作系统默认使用用户目录下的 `.devbox` 保存 DevBox 安装的工具、下载缓存、状态和业务日志。
- DevBox 安装的版本属于托管工具；系统已有工具只读检测，不覆盖其文件。
- 默认不需要管理员权限。首期不提供系统级安装、系统包管理器接管或自动提权。
- Rust 是工具状态、安装结果和任务状态的权威来源，前端只保存查询缓存和交互状态。
- 所有工具通过统一插件契约接入，工具特有规则留在插件内部，通用下载、校验、解压、任务和持久化能力由公共模块提供。

## 核心架构决策

### 统一用户目录

macOS 和 Linux 使用 `$HOME/.devbox`，Windows 使用 `%USERPROFILE%\.devbox`。路径由 Rust 根据操作系统解析，不在前端拼接。

工具资产、下载缓存、安装清单、激活指针、操作记录和业务日志都位于该目录内。开发调试也不使用另一套目录语义，避免开发环境与安装后的应用行为不一致。

### 托管工具与系统工具分离

每个工具可以同时存在多个检测结果：

- DevBox 托管版本：位于 `.devbox/tools`，可以切换、更新和删除。
- 系统版本：来自 PATH、操作系统预装位置或用户已有版本管理器，只读展示版本、路径和健康状态。
- 损坏版本：安装目录存在，但清单缺失、可执行文件不存在或版本验证失败。

系统工具不能被自动改名、移动或覆盖。以后若增加系统级安装，必须作为独立、显式确认的能力实现。

### 激活与命令入口

每个工具可以有一个 DevBox 激活版本。激活由 `state/active/<tool>.json` 指针表示，`.devbox/bin` 中的入口是该指针的派生结果，不作为第二套权威状态。

- 激活只影响 DevBox 管理的工具，不改变系统工具或用户已有版本管理器。
- Unix 入口使用指向具体安装版本的符号链接或稳定包装器；Windows 使用 `.cmd` 包装器调用具体 `.exe`，不依赖创建符号链接的权限。
- 激活成功时先写 active 指针，再重建入口；应用启动和状态异常时根据 active 指针修复入口。
- 入口使用绝对路径并正确引用路径，不把用户可控字符串拼入 Shell 命令。
- 工具管理流程不自动修改 `.zshrc`、`.bashrc`、PowerShell Profile 或系统环境变量。界面展示 `.devbox/bin` 路径和手动配置说明。
- 没有健康激活版本时删除对应入口，避免旧入口继续指向已卸载或损坏的版本。

### 平台与能力模型

平台由操作系统、CPU 架构和必要的运行时环境组成。平台模型区分 `os`、`arch` 和 Linux `libc`；插件负责声明支持范围，通用服务不能根据字符串猜测兼容性。

| 平台 | 架构 | 目标状态 | 约束 |
| --- | --- | --- | --- |
| macOS 11+ | arm64 | 首轮原生验收 | 第一个效果验证平台 |
| macOS 11+ | x86_64 | 发布前验证 | 通用二进制或独立构建需原生验证 |
| Windows 10/11 | x86_64 | 发布前验证 | 不使用管理员权限，包装器使用 `.cmd` |
| Windows 11 | arm64 | 能力可用时支持 | 官方资产缺失时由插件明确禁用 |
| Linux glibc | x86_64 | 发布前验证 | 不以 AppImage 运行时替代系统兼容验证 |
| Linux glibc | aarch64 | 能力可用时支持 | 官方资产和系统依赖需分别验证 |
| Linux musl | 任意 | 暂不启用 | 不静默复用 glibc 资产 |

“目标平台”不代表已经验证。插件必须提供该平台和架构的明确资产，否则界面显示不支持及原因，不下载最接近的资产猜测安装。支持矩阵后续由每个工具的 Release 数据进一步收窄。

### 编译期工具插件

当前版本和首个正式版本使用 Rust 单 crate 内的编译期插件，不加载第三方动态库，也不提供在线插件市场。

这种方式的边界更清晰，插件受 Tauri 应用签名保护，不引入 Rust ABI、动态库分发和跨平台加载问题。新增工具时增加独立插件模块，并在唯一注册表登记；通用安装器和任务引擎不需要感知具体工具。

动态插件可在后续单独设计。届时优先评估独立进程或受限 WebAssembly 沙箱，不能直接向主进程加载任意原生代码。

## 模块组成

```text
React AppLayout
  pages
    features/environment
    features/toolchain
    features/operations
    features/settings
          │
      typed IPC
          │
Tauri IPC
          │
Rust application services
  environment / toolchain / operations / settings
          │
tool plugin registry
  uv | python | node | git
          │
shared infrastructure
  catalog / download / archive / process / registry / path
```

页面负责路由参数和组合，业务模块负责交互、查询和展示模型，Rust 服务负责规则、文件系统、进程和权威状态。模块之间只通过公开接口协作。

业务模块按能力和一致性边界划分，不把所有查询或所有写入分别合并成通用模块。`toolchain` 负责工具库存及其查询，`operations` 负责操作生命周期，并包含该业务自身的任务查询。

### 组合与依赖原则

- 应用入口是唯一组合根：前端由 `AppLayout` 和页面组合业务模块，Rust 由 `lib.rs` 组装插件、服务、基础设施和 IPC。
- 依赖方向为“页面 → 业务公开接口 → IPC 适配 → Rust 应用服务 → 领域模型与插件契约”；基础设施实现通用能力，不反向依赖业务模块。
- 跨模块只通过 `index.ts`、`mod.rs` 等公开出口协作，不读取其他模块内部文件、私有状态或具体适配。
- `operations` 依赖 `toolchain` 的公开库存与插件能力接口，`toolchain` 不反向依赖 `operations`。`operations` 不得直接引用 `plugins/<tool>` 内部文件或写入托管安装库存。
- 一个模块只有一个变化原因。工具发布规则、路径布局或检测方式变化时只修改对应插件；下载、校验、解压或任务状态变化时只修改公共服务。
- 共享层不包含具体工具业务，插件不复制公共能力。不能为了复用把 uv 规则堆入全局 `utils` 或统一 service。
- 交付顺序先形成一条完整链路，再扩展插件；不并行铺开多个半成品工具模块。

## Rust 模块规划

目标结构如下，目录按实际实现逐步建立，不预建空模块：

```text
src-tauri/src/
  main.rs
  lib.rs
  state.rs
  ipc/
    mod.rs
    error.rs
    environment.rs
    toolchain.rs
    operations.rs
  modules/
    environment/
      mod.rs
      model.rs
      service.rs
    toolchain/
      mod.rs
      model.rs
      service.rs
      plugin.rs
      plugins/
        mod.rs
        python/
          mod.rs
        uv/
          mod.rs
          catalog.rs
          detect.rs
          install.rs
    operations/
      mod.rs
      model.rs
      service.rs
    settings/
      mod.rs
      model.rs
      service.rs
  infrastructure/
    mod.rs
    catalog/
    download/
    archive/
    process/
    registry/
    path/
```

各模块职责：

| 模块 | 职责 | 不承担 |
| --- | --- | --- |
| `environment` | 操作系统、架构、常见系统工具位置和运行环境信息 | 工具安装和版本切换 |
| `toolchain` | 系统工具探测、托管安装库存、active 状态、统一查询和插件注册 | 下载传输、后台任务和前端展示 |
| `operations` | 安装、更新、切换、取消、结果、恢复和任务查询；通过公开接口提交库存变更 | 具体工具的资产命名规则和托管安装库存写入 |
| `plugins/uv` | uv 的探测规则、发布目录、资产选择和安装计划 | 通用 HTTP、解压和任务进度 |
| `plugins/python` | Python 系统解释器发现、版本解析和来源提示 | 通用进程、安装和激活能力 |
| `infrastructure` | 下载、校验、解压、进程执行、路径和清单持久化 | 工具业务规则 |

`lib.rs` 只组装应用服务、插件注册表、基础设施和 IPC；`state.rs` 保存服务与任务注册表。领域模型不依赖 Tauri、HTTP、前端 DTO 或具体归档格式。

## 领域模型与标识

| 实体 | 关键字段 | 约束 |
| --- | --- | --- |
| `Platform` | OS、架构、libc、版本 | 由 Rust 检测；插件只能声明支持或不支持 |
| `ToolDescriptor` | `toolId`、名称、插件契约版本、支持平台、默认 channel | `toolId` 是稳定 slug，由编译期注册表唯一确定 |
| `ToolRelease` | `toolId`、上游 `versionId`、channel、发布时间、资产列表 | 版本来自插件目录，排序使用解析后的版本语义 |
| `ToolAsset` | 平台、架构、URL、大小、摘要、归档类型 | 必须与目标平台精确匹配，不使用模糊资产回退 |
| `DetectedInstallation` | 来源、版本、绝对路径、健康状态 | 系统安装只读；同一路径可以只有一个来源 |
| `ManagedInstallation` | 安装 ID、工具、版本、平台、路径、摘要、清单状态 | 一个工具/版本/平台组合最多一个有效安装 |
| `ActiveVersion` | `toolId`、安装 ID、更新时间 | 目标必须存在且通过健康检查，不能指向系统安装 |
| `Operation` | 操作 ID、客户端请求 ID、工具、目标、状态、阶段、序号、错误 | 进入终态后不可回退；同一工具写操作互斥 |

标识规则：

- `toolId` 和 `versionId` 是字符串。上游版本号保留原始含义，不直接拼接为文件系统路径。
- 托管安装目录使用由 `toolId`、规范化版本和平台生成的稳定安全键，原始版本和安装 ID 记录在 `install.json`。
- active 指针引用安装 ID，不引用展示文案或未规范化路径。
- 版本比较使用插件声明的版本语义；无法解析的版本只允许按官方目录顺序展示，不能按字符串比较判断“更新”。
- `stable` 是默认 channel。预发布版本、LTS 和其他 channel 由插件目录显式声明，不从版本字符串猜测。

## 工具插件契约

插件是工具能力的唯一归属点。一个插件至少提供以下信息：

| 能力 | 内容 |
| --- | --- |
| 工具描述 | 稳定插件 ID、显示名称、支持平台、默认 channel、官网和许可证链接 |
| 系统检测 | 常见可执行文件名、已知探测位置、版本命令和输出解析规则 |
| 发布目录 | 官方版本数据来源、channel、分页方式和缓存有效期 |
| 资产选择 | 根据 OS、CPU 架构和运行时环境选择下载资产 |
| 安装计划 | 下载地址、预期摘要、归档格式、可执行文件相对路径和验证命令 |
| 激活方式 | 可执行文件入口和必要的环境变量 |

插件返回类型化计划，公共执行器只接受自身支持的下载、解压和进程能力。插件不能拼接 Shell 命令，也不能直接获得任意文件写入或网络访问权限。

最小插件能力：

| 能力 | 输入 | 输出 |
| --- | --- | --- |
| `supports` | `Platform` | 支持状态或不支持原因 |
| `detect` | 只读环境与探测上下文 | 系统安装候选和版本解析计划 |
| `list_releases` | channel、平台、缓存上下文 | 官方 Release 和资产 |
| `select_asset` | Release、`Platform` | 精确匹配的资产或不可用原因 |
| `install_plan` | 资产、托管目录布局 | 下载、校验、解压、入口和验证计划 |
| `validate` | 暂存产物、平台、预期版本 | 健康结果或类型化错误 |
| `activation` | 托管安装、入口布局 | 可执行入口和环境变量描述 |

插件契约包含 `contractVersion`。Managed 安装清单记录安装时使用的插件和契约版本；未知或过新版本不能静默按当前规则解释。当前注册第一方 `uv`、`python`、`node`、`npm`、`pnpm`、`git`、`bash` 和 `zsh` 检测插件，注册表在 `lib.rs` 组合，不进行目录扫描或运行时加载。

插件规则：

- 插件只依赖共享领域类型和能力接口，不依赖 Tauri、IPC、页面或数据库实现。
- 插件不调用其他插件；跨工具流程由 `toolchain` 或上层应用服务协调。
- 工具特有逻辑放在插件目录内，通用逻辑不得堆入插件，也不得在插件中复制下载器、解压器或任务状态机。
- 插件输出包含稳定的 `toolId`、版本和平台信息，错误使用可映射为稳定错误码的类型。
- 安装链路以 `uv` 为第一个完整实现；Python 系统检测作为独立插件运行，不把 uv 写死在通用服务中。
- 插件不直接写 active 指针、安装清单或 `.devbox/bin`；验证通过后，由 `operations` 调用 `toolchain` 库存服务的公开提交接口执行。

## 前后端职责边界

| 能力 | 前端职责 | Rust 职责 |
| --- | --- | --- |
| 页面与路由 | 路由、筛选、排序、选择状态和展示状态 | 不承担页面展示逻辑 |
| 系统检测 | 发起查询、展示结果和刷新反馈 | 探测 OS、架构、PATH 和工具版本，返回快照 |
| 版本目录 | 展示版本、渠道和筛选条件 | 获取官方目录、校验资产映射并使用缓存 |
| 安装与更新 | 提交意图、展示进度、请求取消 | 排队、下载、校验、解压、验证、激活和清理 |
| 当前版本 | 展示激活状态并提交切换意图 | 维护安装清单、激活指针和健康状态 |
| 设置 | 表单草稿、主题偏好和即时校验反馈 | 验证业务设置、持久化和处理格式迁移 |
| 错误与日志 | 按稳定错误码展示，不解析错误文案 | 记录内部诊断，返回安全错误 DTO |

边界规则：

- 前端可以为了交互体验提前校验，但 Rust 必须重新验证工具 ID、版本、操作状态和路径。
- 组件、页面和状态容器不直接访问文件系统、Shell、任意网络地址或业务 Tauri 原始消息。
- 前端不保存业务权威数据。主题和界面偏好可以使用浏览器存储；工具、安装、激活和任务状态不能。
- 文件路径只作为查询结果展示，不能由前端拼接后回传作为写入目标。
- 前端显示“成功”必须来自 Rust 的权威完成状态或重新查询结果，不能只依据本地按钮状态。

## 前端组合边界

前端按业务能力建立模块：

```text
src/features/
  environment/
    index.ts
    api.ts
    contracts.ts
    model.ts
    hooks/
    components/
  toolchain/
  operations/
  settings/
```

- 页面只组合业务模块公开出口和通用 `Page`、shadcn 组件。
- 组件通过 props 接收展示数据，通过回调表达意图，不直接调用 Tauri。
- 查询、任务订阅和错误转换位于模块 hook 与 API 适配层。
- 跨模块交互由页面或按需建立的 `app/` 组合层协调，不读取其他模块私有 store。
- 主题等 UI 偏好可以持久化；工具状态、安装路径和任务状态不能存入浏览器存储。
- 模块查询状态必须区分未加载、加载中、成功空结果、成功有数据和失败，不能用空列表代替失败。
- 所有异步查询按业务作用域和请求代次丢弃旧响应，切换工具或重新进入页面后旧响应不能覆盖新状态。
- 页面卸载不等于 Rust 任务取消。重新进入页面必须重新查询任务和工具权威状态，并重新建立进度订阅。

建议页面结构：

| 路由 | 职责 |
| --- | --- |
| `#/` | 概览：系统信息、已检测工具、可更新数量和当前任务 |
| `#/tools` | 工具列表：系统版本、托管版本、状态和主要操作 |
| `#/tools/:toolId` | 工具详情：版本、安装位置、可用版本、切换和更新 |
| `#/tasks` | 任务中心：进度、取消、错误和历史 |
| `#/settings` | 托管目录、网络、缓存和后续 Shell 集成设置 |

示例 `#/projects` 路由、团队和项目导航已从活动应用组合中移除，当前导航为概览、工具和设置。模板遗留的未引用组件不代表这些产品能力存在。

## 用户目录布局

```text
<user-home>/.devbox/
  bin/                              # 从 active 指针派生的可执行入口或包装器
  tools/
    uv/
      <installation-key>/
        install.json                # 该版本的安装清单
        ...                         # 插件声明的工具文件和原始版本信息
  state/
    active/
      uv.json                       # 激活版本指针
    operations/
      <operation-id>.json           # 任务状态、阶段和最终错误
    locks/                          # 跨进程工具锁和全局维护锁
  cache/
    releases/                       # 可丢弃的版本目录缓存
    downloads/                      # 按摘要寻址的下载缓存和 .part 文件
  staging/                          # 解压和验证中的临时目录
  backups/                          # 配置和清单迁移前备份
  logs/                             # 已脱敏的业务日志
  config.json                       # 应用设置和格式版本
```

`<user-home>/.devbox` 在所有平台保持同一语义。Windows 的可执行文件使用 `.exe` 扩展名，`bin/` 入口可以使用 `.cmd` 包装器；Unix 平台可以使用符号链接。具体实现由路径适配层决定。

目录由 Rust 在首次启动时创建。Unix 下目录默认仅当前用户可读写，文件使用仅用户可读写权限；Windows 依赖当前用户目录 ACL。DevBox 不跟随 `.devbox` 内指向目录外部的不安全符号链接写入数据。

### 状态所有权

| 状态 | 唯一所有者 | 约束 |
| --- | --- | --- |
| 系统工具探测结果 | `toolchain` | 只读，不修改系统工具 |
| 托管安装清单与工具文件 | `toolchain` | 仅库存服务写入；`operations` 提交验证通过的安装计划 |
| active 指针与 `.devbox/bin` | `toolchain` | 只指向健康托管安装；入口是指针的派生结果 |
| 操作记录与任务状态 | `operations` | 按 `operationId` 隔离，终态不可回退 |
| Release 缓存 | `toolchain` | 可删除或重建，不作为已安装版本的唯一记录 |
| 前端查询缓存 | 对应 feature | 只是快照派生数据，不构成第二套工具真相 |

- 每个 `install.json` 和实际工具文件是“该版本是否存在”的权威来源。
- 激活指针决定 DevBox 当前选择哪个托管版本，使用临时文件加原子替换更新。
- 启动或进入工具页时校验安装清单与可执行文件，发现缺失时标记为损坏，不静默创建空安装。
- `.devbox/bin`、Release 缓存和下载缓存都是派生数据，可以从 active 指针和安装清单重建或清理。

安装清单至少包含格式版本、插件 ID、工具版本、平台、架构、来源、摘要、安装时间、可执行文件相对路径和健康状态。时间使用带时区的 RFC 3339 字符串。

### 持久化格式与迁移

- `config.json`、`install.json`、active 指针和操作记录都有独立 `schemaVersion`，不能用一个全局版本推断所有文件格式。
- 写入使用同目录临时文件、刷新和原子替换；替换前验证现有文件并保留一份可恢复备份，损坏内容不能覆盖有效备份。读取到截断或损坏文件时优先恢复备份，恢复失败则将状态标记为需要修复，不能静默覆盖。
- 状态迁移在全局维护锁内执行，按版本顺序前向迁移。遇到高于当前应用支持的格式时停止写入并提示升级 DevBox。
- 操作记录在任务开始、阶段变化和终态时持久化。进度百分比的瞬时变化可以只通过 channel 推送，不必每个字节写盘。
- 安装清单与工具文件不一致时，以实际存在且通过验证的结果为准，并在不破坏文件的前提下重建索引。

### 清理与保留

- 下载缓存按摘要复用，复用前必须重新校验摘要；失败或不完整临时文件可以安全删除。
- 默认清理超过 7 天或使缓存超过 2 GiB 的下载，以及超过 24 小时的失败暂存。数值进入设置后可以调整。
- 操作记录默认保留最近 200 条或 30 天，日志默认保留 14 天或 10 MiB。
- 清理只删除缓存、日志和已完成/失败的操作记录，不删除已安装版本或 active 指向。
- 卸载托管版本是显式操作；active 版本必须先切换或停用后才能删除。

### 设置边界

- `.devbox` 根目录由用户主目录固定解析，前端不提供任意路径改写入口。
- 主题和侧栏等纯界面偏好由前端保存；缓存保留、网络和工具策略等业务设置由 Rust 校验并写入 `.devbox/config.json`。
- 代理凭据等敏感配置不能在浏览器存储中保存；未来若支持，必须使用操作系统凭据存储或明确加密方案。
- 当前代理设置支持系统、直连和手动 HTTP/SOCKS5H，默认使用系统模式；系统模式读取操作系统静态 HTTP/HTTPS 代理，Linux 无统一系统代理时使用代理环境变量。设置快照返回当前实际生效的 HTTP/HTTPS 路由、来源和认证需求；来源按最终选中路由的地址与认证信息判断，代理凭据不进入前端，代理设置不保存账号密码。
- 设置更新由单一写入线程串行提交，锁不跨越文件 I/O；当前写入后由响应返回新 revision，多窗口变更事件随事件链路接入。
- 操作系统代理读取通过阻塞任务执行；设置模块把基础设施返回的读取结果转换为自身模型后再交给 IPC，不向业务接口泄漏网络适配类型。
- 修改设置不得静默删除已安装版本；缓存或日志策略变化只影响派生数据。

## 系统检测

检测由环境模块和工具插件共同完成，不扫描整个磁盘。

1. 环境模块在启动时识别操作系统版本、CPU 架构、用户主目录、账户默认 Shell、内存、主目录所在卷容量和 GPU 等规格；查询只读取快照，不做持续采样或实时用量统计。
2. 托管检测读取 `.devbox/tools` 下的安装清单。
3. 系统检测使用账户默认 Bash/Zsh 的登录环境 PATH，按顺序选择每个工具的第一个可执行文件；Bash、Zsh 使用账户记录的默认 Shell 路径。
4. 对当前可执行文件执行版本命令，按插件规则解析并记录绝对路径、来源和健康状态。探测 npm/pnpm 等脚本时复用同一登录 PATH。
5. 工具快照保留已扫描的托管安装，但 `currentInstallationId` 只指向当前生效安装，界面每张工具卡只展示该项。

当前硬件规格检测以 macOS 为主：macOS 提供系统版本、内存、主目录所在卷容量、GPU 和账户默认 Shell，Linux 提供系统版本、内存、容量和账户默认 Shell，Windows 目前只提供系统版本。未实现的字段显式返回 null，界面显示“未知”，待对应平台原生验证后补齐。

登录 PATH 通过默认 Bash/Zsh 的固定 `-l -c` 打印命令读取，启动过程可能执行用户登录配置；命令不接受前端输入，并受超时和输出上限约束。

检测只读运行，不安装、不更新、不修改 PATH。系统工具版本异常不能阻止 DevBox 展示其他工具。

## 安装与任务流程

通用操作执行器负责完整流水线：

1. 校验工具、版本、channel 和平台属于插件目录，并取得对应工具锁。
2. 检查 `.devbox` 权限、可用磁盘空间和路径长度，预留下载、解压和回滚空间。
3. 下载资产到 `.devbox/cache/downloads` 的临时文件，或复用校验通过的缓存资产。
4. 校验摘要、文件大小和文件类型。
5. 解压到 `.devbox/staging/<operation-id>`，执行归档安全检查。
6. 验证可执行文件和版本输出。
7. `operations` 将验证通过的暂存产物和安装计划提交给 `toolchain` 库存服务。
8. `toolchain` 原子写入托管安装目录与清单，更新 active 指针并修复 `.devbox/bin` 入口。
9. `toolchain` 增加 revision 并发布工具状态事件；`operations` 重新确认健康状态，释放工具锁并进入 `succeeded`。

操作状态与执行阶段是两个独立字段。状态表示任务生命周期：

```text
queued -> running
queued | running -> cancel_requested
running -> succeeded | failed
cancel_requested -> cancelled
queued | running | cancel_requested -> interrupted
```

`succeeded`、`failed`、`cancelled` 和 `interrupted` 是终态，进入终态后不得回退。`interrupted` 由启动恢复识别进程异常退出后写入。

`phase` 表示运行中的执行阶段：

```text
resolving -> downloading -> verifying -> extracting
          -> validating -> activating -> finalizing
```

阶段只在 `running` 状态内推进。取消请求到达后不再发起新阶段，协作停止当前子操作并完成暂存清理，再将状态转换为 `cancelled`。失败和取消都必须清理暂存目录，保留原有激活版本。更新时先并排安装新版本，验证通过后才切换，旧版本保留用于回滚。

目标约束是同一工具同时只允许一个写操作，不同工具可以有限并发；首个交付全局最多一个安装类写操作。每个操作有唯一任务 ID、工具 ID、目标版本和单调进度，取消是显式请求，前端断开不自动等于 Rust 任务取消。

### 更新与回滚

- 默认目标是最新 Stable；用户选择精确版本时以目录中的 `versionId` 为准。
- 更新采用并排安装，不原地覆盖当前版本。新版本通过验证后激活，旧版本继续保留。
- 回滚使用 `activate_version` 指向原安装，不重新下载；按时间自动回滚属于后续配置能力。
- 更新失败、摘要错误、版本验证失败或取消都保持原 active 指针不变。
- 目录中没有适用当前平台的资产时，界面显示不可安装原因，不自动尝试其他操作系统资产。

### 卸载

- 只有 DevBox 托管安装可以卸载，系统工具不允许删除。
- active 版本必须先切换或停用后再卸载；卸载命令不能静默选择另一个版本。
- 卸载删除该版本目录、安装清单和派生入口，并从操作记录中保留可审计结果。
- 卸载开始前取得同一工具锁；卸载完成后重新扫描该工具的托管安装和 active 状态。
- 卸载 UI 属于后续交付；领域模型和命令边界保留该能力，避免把安装目录当成永久不可撤销数据。

## 异步、并发与恢复

### Rust 任务模型

- command 只做边界转换、权限和输入校验，然后调用应用服务；长任务由应用服务登记到任务注册表并异步执行。
- 每个任务有唯一 `operationId`、`clientRequestId`、工具作用域、状态机、取消令牌、进度序号和最终错误。
- 网络下载、进程等待和任务调度使用异步执行；解压、哈希计算和其他阻塞文件操作进入受控阻塞工作线程。
- 锁只保护短时一致性更新，不跨越 await、下载、解压或子进程等待，也不以全局锁覆盖所有工具。
- 子进程输出、下载缓冲和进度队列都有容量上限。高频进度可以合并推送，不能无限堆积。
- 首个交付全局最多一个安装类写操作；查询可以并发。领域模型预留按工具串行的约束，扩展到多工具时启用有限并发。

### 多实例与文件锁

- DevBox 默认只运行一个应用实例；再次启动时聚焦已有窗口，不创建第二个写入者。
- 单实例限制只解决正常 UI 使用，正确性仍由 `.devbox/state/locks` 下的跨进程独占文件锁保证。
- 安装、更新、激活、卸载和修复按 `toolId` 获取工具锁；缓存清理、迁移和全局恢复获取维护锁。
- 锁由操作系统在进程退出时释放，不依赖仅记录 PID 的软锁。获取失败返回 `OPERATION_CONFLICT`，不得继续写入。
- 锁只覆盖操作生命周期，不跨越前端 channel；取消、失败和完成都必须释放，进程异常退出由操作系统回收。

### 取消与退出

- 取消是请求，不立即宣告操作完成。Rust 将任务标记为取消请求，协作停止下载或子进程，清理暂存目录后再进入 `cancelled`。
- 取消完成前，任务仍占用对应工具的写操作槽位，避免并发安装覆盖同一目录。
- 前端关闭页面、刷新或失去 channel 不会取消 Rust 任务。
- 应用进程退出会终止后台任务。下次启动时，遗留的进行中记录标记为 `interrupted`，清理未完成暂存目录，已有激活版本保持不变。
- 任务中断原因和恢复动作必须可查询，不能把遗留任务静默当成成功。

### 失败、重试与恢复

- 查询命令失败可以安全重试；开始写入的超时重试必须复用同一个 `clientRequestId`，由 Rust 返回已有操作。
- 下载和 release 查询可以按幂等 GET 规则自动重试；摘要错误、归档不安全或版本验证失败不做盲目自动重试。
- 结果不明确的激活或文件移动不能直接重复执行，必须先查询权威状态再决定下一步。
- 下载使用临时文件，校验通过后才进入解压；安装使用单独 staging，验证通过后才移动到版本目录。
- 启动恢复扫描安装清单、激活指针和 staging。激活指针指向缺失版本时标记异常，不自动选择任意其他版本冒充成功。

### 前端异步规则

- 每个 invoke 都处理成功、业务错误和传输错误，不能 fire-and-forget。
- 查询请求的超时只代表等待响应超时，不代表 Rust 后台任务被取消。
- 同一查询并发触发时按作用域合并请求；新作用域或新代次请求会使旧响应失效。
- channel 断开或重挂载后调用 `get_operation` 恢复状态，再按需要重新订阅进度。
- 任务按钮在提交后进入 pending，等待 Rust 接受结果；重复点击由前端禁用和 Rust 去重共同防护。
- 进度只驱动展示，不直接写入权威缓存。终态必须以任务快照或重新查询工具状态为准。

## 通信契约

### 通道选择

| 通道 | 使用场景 | 约束 |
| --- | --- | --- |
| command | 查询快照、启动任务、取消任务、切换版本 | 短请求返回确认或结果，不等待安装完成 |
| channel | 当前任务的下载、校验、解压和验证进度 | 携带 `operationId`、单调 `sequence` 和阶段 |
| event | 工具状态、目录和任务终态的低频通知 | 携带资源 ID 与 revision，只作为刷新信号 |

业务 IPC 只能由各业务模块的 API 适配层调用。页面、展示组件和纯展示状态不拼接命令名，也不直接处理 Tauri 原始消息。

### 命令边界

| 命令 | 实现状态 | 用途 |

| `list_tools` | 已实现 | 查询工具、系统安装、托管安装和更新状态 |
| `refresh_tools` | 已实现 | 重新执行系统安装和托管安装检测 |
| `get_settings` | 已实现 | 查询版本化设置；返回代理配置和当前系统代理读取结果 |
| `update_settings` | 已实现 | 更新经过 Rust 校验的代理设置，并返回包含系统代理读取结果的新快照 |
| `test_proxy` | 已实现 | 使用当前输入访问固定 HTTPS 目标，验证代理连通性 |
| `get_tool` | 规划 | 查询单个工具详情和全部检测结果 |

核心请求和响应：

| DTO | 关键字段 |
| --- | --- |
| 查询快照 | `bootId`、`revision`、`generatedAt` 和资源数据 |
| `StartInstallRequest` | `clientRequestId`、`toolId`、`versionId` |
| `OperationAccepted` | `bootId`、`operationId`、`toolId`、`versionId`、`state`、`revision` |
| `OperationSnapshot` | `bootId`、`operationId`、`toolId`、`versionId`、`state`、`phase`、`sequence`、进度、时间和错误 |
| `OperationProgress` | `bootId`、`operationId`、`sequence`、`phase`、已下载/总字节、可选安全提示 |
| `ToolStateEvent` | `bootId`、`toolId`、`revision`、`reason` |
| `CatalogStateEvent` | `bootId`、`toolId`、`revision`、`updatedAt` |
| `OperationStateEvent` | `bootId`、`operationId`、`toolId`、`state`、`sequence`、`revision` |
| `IpcError` | 稳定 `code`、可展示 `message`、可选类型化 `details` |

契约要求：

- Rust IPC DTO 是契约源，TypeScript 类型与其一一对应；引入类型生成后，生成物禁止手改。
- JSON 字段使用 camelCase，标识符使用字符串，时间使用带时区的 RFC 3339 字符串，revision 和 sequence 使用十进制字符串。
- `start_install` 和 `start_update` 返回“操作已登记”，不返回“安装已成功”。成功必须来自终态查询或明确的完成状态事件。
- 前端传递 `clientRequestId`，Rust 对重复请求去重并返回同一个操作，避免双击或超时重试创建多次写入。
- 去重记录至少保留到对应操作记录被清理；同一 ID 但请求内容不同必须拒绝。
- 前端只传工具 ID、版本 ID 和操作意图。下载 URL、摘要、归档类型和安装路径由 Rust 插件解析。
- 错误按稳定错误码处理，不解析 `message`。内部路径、堆栈、凭据和原始下载错误不进入用户错误 DTO。

首批稳定错误码：

| 错误码 | 含义 |
| --- | --- |
| `INVALID_INPUT` | 请求字段缺失、ID 格式错误或内容不一致 |
| `TOOL_UNKNOWN` | 插件注册表中不存在该工具 |
| `VERSION_UNKNOWN` | 版本不属于当前工具目录 |
| `PLATFORM_UNSUPPORTED` | 插件没有适配当前平台的资产 |
| `OPERATION_CONFLICT` | 同一工具已有写入操作或跨进程锁冲突 |
| `NETWORK_UNAVAILABLE` | 网络不可用且没有可信缓存 |
| `DOWNLOAD_FAILED` | 下载失败、响应异常或大小超限 |
| `CHECKSUM_MISMATCH` | 摘要或签名验证失败 |
| `ARCHIVE_UNSAFE` | 归档损坏、路径穿越或条目超限 |
| `VALIDATION_FAILED` | 可执行文件或版本验证失败 |
| `DISK_SPACE_INSUFFICIENT` | 下载或安装空间不足 |
| `PERMISSION_DENIED` | `.devbox` 或目标文件无写权限 |
| `FILE_BUSY` | 目标文件被占用或无法替换 |
| `ACTIVE_VERSION_PROTECTED` | 试图卸载当前激活版本 |
| `CANCELLED` | 操作按请求取消并完成清理 |
| `INTERRUPTED` | 应用退出或崩溃导致任务中断 |
| `INTERNAL` | 未分类内部错误，只暴露通用可展示信息 |

## 状态同步

Rust 是环境、工具、安装和任务状态的唯一权威来源。前端查询缓存只是权威快照的派生数据。

### Revision 协议

- Rust 进程启动时生成新的 `bootId`。同一作用域的 `revision` 在本次进程生命周期内单调递增，重启后允许重新计数。
- 每个查询 DTO 包含 `bootId`、所属资源作用域的 `revision` 和生成时间。
- revision 只在同一作用域内比较，作用域至少分为环境、工具链、每个工具的目录和每个任务。
- 前端缓存按 `bootId + 作用域` 保存；bootId 变化时丢弃全部业务查询缓存并重新查询，不能把不同应用进程的 revision 互相比较。
- 工具状态、目录和任务终态事件包含相关 ID 与 revision，不携带完整工具对象，避免前端形成第二套状态。
- 前端保留当前作用域已经应用的最高 revision。收到更低 revision 的快照时丢弃并重新查询，不能覆盖新状态。
- 同一任务的进度消息使用单调 `sequence`。乱序或重复消息不能倒退进度或覆盖终态。
- 发现 sequence 跳跃时不根据缺失消息推演状态，直接调用 `get_operation` 恢复快照。
- 事件不是唯一事实来源。收到事件后重新查询，页面重新挂载后也重新查询。

### 挂载与重连流程

1. 页面先注册相关 event 监听。
2. 查询任务列表，为仍在运行的任务建立 channel 订阅。
3. 查询环境、工具和版本快照。
4. 查询返回后，如果期间收到更高 revision 的事件，立即重新查询对应作用域。
5. 任务终态事件到达后查询 `get_operation`，并失效工具列表与对应工具详情。
6. 页面卸载时释放监听，但 Rust 任务继续运行；重新进入页面时重复以上流程。

查询缓存作用域至少包含 `environment`、`tools`、`tool:<toolId>`、`releases:<toolId>`、`operations` 和 `operation:<operationId>`。旧作用域响应按请求代次丢弃。

### 失效关系

| 事件 | 需要失效或重新查询 |
| --- | --- |
| `ToolStateEvent` | 工具列表、对应工具详情、概览汇总 |
| `OperationStateEvent` | 任务列表、对应任务详情；终态同时失效对应工具 |
| 目录刷新完成 | 对应工具的 release 列表和更新提示 |

安装和切换版本不使用乐观写入。操作进行中显示 pending 或运行状态；Rust 返回成功并重新查询后才能把新版本显示为已激活。查询失败时保留可用的旧数据，不能清空为“没有安装”。

典型异步链路：

```text
UI -> start_install(clientRequestId, toolId, versionId)
Rust -> OperationAccepted(operationId)
UI -> subscribe_operation(operationId, channel)
Rust -> channel(progress sequence...)
Rust -> OperationStateEvent(succeeded)
UI -> get_operation(operationId) + list_tools()/get_tool(toolId)
UI -> 使用权威快照更新任务与工具状态
```

## 端到端主链路

```text
页面打开
  -> 前端注册 event，查询 task/tool/release 快照
  -> Rust 读取 .devbox，执行只读检测并按 bootId 生成 revision
  -> 前端展示每个工具的当前生效安装和默认 Shell

用户安装 uv 版本
  -> feature hook 生成 clientRequestId
  -> command 校验输入，应用服务取得工具锁并登记 Operation
  -> 插件解析官方 Release、平台资产、摘要和安装计划
  -> 下载缓存 -> 摘要校验 -> 安全解压 -> 版本验证
  -> operations 提交验证产物与安装计划
  -> toolchain 写入安装库存 -> 更新 active -> 修复 .devbox/bin
  -> channel 推送阶段和进度
  -> 终态 event 通知前端
  -> 前端查询 operation/tool 权威快照，更新页面
```

这条链路中，页面不直接接触下载地址、文件路径或进程；插件不直接写 active 指针或安装清单；`operations` 不直接写工具库存；通用执行器不包含 uv 专有规则；Rust 状态在每一步失败时保持可查询和可恢复。

## 安全与信任边界

### 发布目录与下载

- 每个插件声明允许的官方 HTTPS 主机；Release 元数据、资产和摘要必须来自同一官方发布来源。
- 没有可验证摘要的资产不能进入安装计划；摘要不能从用户输入或任意镜像页面临时补齐。
- 重定向只能到允许的 HTTPS 主机，并设置次数上限；不能接受降级为 HTTP 或把凭据带到新主机。
- 下载前限制声明大小，下载中限制实际字节数，下载后校验摘要、文件大小和文件类型。
- 缓存资产每次复用都重新校验摘要，用户可写的 `.devbox/cache` 不能被视为可信输入。
- 有官方签名时继续校验签名；签名或摘要失败直接终止，不使用“跳过校验”或最接近资产回退。
- 官方目录不可用且缓存过期时，只展示缓存元数据并标明过期；没有可信资产时不允许安装。

### 文件与进程

- 解压拒绝绝对路径、父目录穿越、危险符号链接、设备文件和超出大小限制的条目。
- 所有写入目标规范化后必须位于 `.devbox` 的目标子目录内，不能通过版本 ID 或插件输入逃逸。
- 子进程使用可执行文件路径和参数数组启动，不通过 Shell 拼接命令。
- 版本探测、安装验证和工具执行使用受控环境变量，不把前端提供的环境变量直接注入子进程。
- 工具输出有超时、容量上限，并区分退出码、版本解析失败、网络失败和取消。
- active 指针只引用 Rust 验证过的托管安装，不执行任意路径。
- 用户目录路径、资源 ID、版本、channel 和前端请求均视为不可信输入，由 Rust 重新校验。
- 内部路径、堆栈、凭据和原始下载错误不进入可直接展示的错误消息。
- 工具管理不执行管理员权限操作，不写入系统工具目录，不自动修改 Shell 配置。

## 非功能与失败矩阵

| 情况 | 预期行为 | 恢复方式 |
| --- | --- | --- |
| 无网络 | 查询显示离线或使用过期目录；安装只有可信缓存资产时继续 | 恢复网络后重试，保留 active |
| 目录接口超时 | 返回可重试错误，不创建安装写入 | 使用退避重试或读取过期缓存 |
| 磁盘空间不足 | 安装前拒绝并显示所需空间，不开始解压 | 清理缓存或用户释放空间后重试 |
| `.devbox` 无写权限 | 状态查询可继续，写入返回权限错误 | 修正目录权限，不自动提权 |
| 磁盘满或写入中断 | 标记失败并清理暂存，不改变 active | 重试安装，复用校验通过的下载 |
| Windows 文件被占用 | 返回可重试文件错误，不删除使用中的版本 | 关闭占用进程后重试 |
| 路径过长或名称非法 | 拒绝该安装位置并给出可操作错误 | 调整 `.devbox` 路径；不静默换目录 |
| 摘要或签名错误 | 终止安装并删除不可信产物 | 重新下载官方资产，不绕过校验 |
| 归档损坏或不安全 | 终止解压，清理 staging | 刷新目录并重新下载 |
| 版本输出无法解析 | 安装视为未通过验证，不激活 | 使用兼容版本或修复插件探测规则 |
| 进程超时或被取消 | 终止子进程树并清理暂存 | 查询任务状态后重试 |
| 应用异常退出 | 下次启动标记任务中断并清理 staging | 保留 active，重新安装或继续查询 |
| 安装清单损坏 | 尝试备份恢复，否则标记损坏 | 使用修复命令或重新安装版本 |
| 多实例同时写入 | 后取得工具锁的操作返回冲突 | 等待前一任务结束，不并发写入 |

网络请求使用连接超时、空闲超时和总重试预算；进度更新按时间或阶段合并，不能依赖每个网络分片。代理已接入系统、直连与手动 HTTP/SOCKS5H 配置，代理认证、镜像和离线目录管理作为后续配置能力接入，并保持同一摘要和签名策略。下载任务在开始时捕获当次 `NetworkRoute`，执行期间不中途切换；设置变更只影响之后开始的任务。

### 性能与资源目标

- 系统检测不扫描整个磁盘，不在 UI 线程执行进程探测，不因目录刷新阻塞应用启动。
- 下载、摘要计算和解压采用流式或受控块处理，不把完整归档或工具包读入内存。
- 查询、事件、channel 和子进程输出都有容量上限；单个任务不能无限占用内存或文件句柄。
- 启动时优先恢复清单和 active 状态，系统工具探测和网络目录刷新可以异步完成。
- 进度消息允许合并，但任务状态变化、错误和终态不能丢失；前端以快照恢复缺失进度。

## 可观测性、隐私与诊断

- Rust 日志使用结构化字段至少包含 `operationId`、`toolId`、阶段、错误码、耗时和平台。
- 日志不记录用户凭据、前端完整请求体、任意环境变量或可执行文件的敏感输出。
- 操作记录保存阶段和错误码，不把下载地址中的临时签名参数持久化。
- 日志和操作记录按前文保留策略轮转；清理失败要记录，不得影响工具安装完成。
- 默认不收集遥测，不向第三方发送环境、路径、工具版本或使用记录。
- 诊断导出由用户显式触发，内容应说明包含的系统信息和日志字段；导出前做路径和敏感值脱敏。

## DevBox 应用发布与更新边界

工具版本更新和应用自身更新是两条独立链路。本架构中的“更新”默认指托管工具版本，不包含升级 DevBox 可执行文件。

- DevBox 自动更新属于独立产品能力，不混入 uv 安装任务。
- 发布构建按 Tauri 现有目标生成 macOS `.app`/`.dmg`、Windows NSIS/MSI 和 Linux AppImage/deb/rpm；各平台产物必须原生验证。
- 发布前配置 macOS 签名与公证、Windows 代码签名和 Linux 包签名策略；签名失败不能发布为正式版本。
- 应用自身后续若增加更新器，必须使用独立签名和回滚语义，不能复用用户 `.devbox` 中的工具安装状态。
- 持久化格式与应用版本兼容策略由迁移规则决定；降级应用遇到未知新格式时停止写入并提示升级。

## 当前交付范围

首个完整安装链路以 uv 为对象，Python、Node.js 和 Git 按能力复用顺序进入安装范围。Python 系统检测作为独立插件验证多工具扩展边界。一个工具可以管理多个版本，至少使用两个官方 Stable 版本验证安装、切换和回滚边界。

默认选择最新 Stable。官方目录不可用且没有可用缓存时展示离线错误；已安装版本和检测结果仍然可查询。

首个完整安装链路范围：

- 识别当前 OS、架构和用户 `.devbox` 根目录。
- 检测 uv 的系统安装和 DevBox 托管安装。
- 查询并展示 uv Stable 版本。
- 安装指定版本，显示进度，支持取消。
- 验证产物后激活，生成 `.devbox/bin/uv` 或 Windows `.cmd` 入口，不自动修改 Shell 配置。
- 关闭并重新打开应用后恢复托管版本、active 指针和入口。
- 安装第二个版本并切换，验证版本更新和回滚所需的数据边界。
- 展示安装路径、当前激活版本和失败原因。
- 多实例或并发写入返回操作冲突，不损坏当前安装。

安装链路页面状态：

| 状态 | 展示与操作 |
| --- | --- |
| 初始加载 | Skeleton；不显示“未安装”，等待 Rust 快照 |
| 查询失败 | 显示错误码、重试和保留的旧数据；不显示成功空列表 |
| 仅系统安装 | 显示系统版本、路径和“未安装 DevBox 版本” |
| 已安装未激活 | 显示版本、路径和激活按钮 |
| 已激活 | 显示 active 标记、入口路径和可更新状态 |
| 有更新 | 显示最新 Stable 和更新按钮，不自动更新 |
| 安装或更新中 | 显示阶段、进度、operationId 和取消按钮；禁用冲突写入 |
| 已取消或中断 | 保留终态原因，允许重新开始；active 不改变 |
| 安装损坏 | 显示损坏版本和修复/重新安装建议，不提供激活 |
| 离线 | 显示目录不可更新；已安装状态仍可查询 |

首个安装链路的目标命令面：

- 查询：`get_environment`、`refresh_tools`、`list_tools`、`get_tool`、`list_tool_releases`、`refresh_tool_releases`、`list_operations`、`get_operation`。
- 写入：`start_install`、`start_update`、`activate_version`、`cancel_operation`、`subscribe_operation`。
- 当前提供代理设置与连接测试 UI；卸载、缓存清理、安装修复和 Shell 集成 UI 尚未提供。

工具安装用户路径：

1. 首次启动显示系统信息和 uv 未安装状态。
2. 选择最新 Stable 并开始安装，页面显示任务阶段和进度。
3. 安装验证完成后激活，显示版本、安装路径和可执行入口。
4. 关闭并重新打开应用，状态保持一致。
5. 安装第二个版本并切换，旧版本仍可切换回去。
6. 取消安装或制造摘要失败，任务失败但当前 active 和旧版本不受影响。

交付顺序：

1. 建立前后端 DTO、稳定错误码、模块骨架、工具导航和页面状态模型。
2. 建立 `.devbox` 布局、权限、持久化格式、备份和跨进程锁。
3. 完成环境查询、uv 与 Python 系统检测和带 `bootId + revision` 的前端查询状态。
4. 完成任务注册表、操作记录、channel 进度、终态 event、重连查询和启动恢复。
5. 完成 uv 官方目录查询、缓存、平台能力判断和资产选择。
6. 完成下载、摘要校验、暂存解压、版本验证、激活和 `.devbox/bin` 入口。
7. 完成第二版本安装、切换、取消、摘要失败、磁盘不足、重启恢复和多实例冲突验证。
8. 在 macOS arm64 完成效果验收；在 Windows x64 和 Linux glibc x64 完成发布前原生验证。

后续交付范围：

- Python 复用 uv 托管运行时，并接入安装、验证和激活计划。
- Node.js 和 Git 通过独立插件接入安装链路。
- 第三方插件在独立进程或受限 WebAssembly 沙箱中运行。
- 系统级安装、自动提权和系统包管理器接管按独立权限模型设计。
- PATH 和 Shell 配置集成按显式用户配置接入。
- 镜像、代理认证、离线目录和应用更新调度进入受控配置链路。
- 批量操作和多工具并发调度按资源锁与任务容量扩展。
- 托管版本卸载、缓存设置、缓存清理和安装修复形成完整操作界面。

## 完成判定

首个完整安装链路先在 macOS arm64 完成真实用户路径。多平台发布前完成 Windows x64 和 Linux glibc x64 的原生验证；macOS x86_64 和 Windows arm64 在对应官方资产和原生验证完成后标记支持。

功能验收：

- 未安装 uv 时能正确显示系统状态，检测过程不产生安装写入。
- 安装成功后，uv 可执行文件、安装清单和激活指针都位于用户 `.devbox`。
- `.devbox/bin/uv` 或其 Windows 包装器指向当前 active 版本；切换后入口同步更新。
- 关闭并重新打开应用后，托管版本、激活状态和安装路径保持一致。
- 安装另一个版本后可以切换，旧版本仍可恢复。
- 下载失败、摘要错误、磁盘不足或用户取消不会破坏当前激活版本。
- 系统已有 uv 与 DevBox 托管 uv 同时存在时，两者状态不会混淆。
- 两个应用实例或两个写入请求竞争同一工具时，只允许一个操作，失败方得到明确冲突错误。
- 页面重载、channel 断开和应用重启后，任务和工具状态可以从 Rust 查询恢复。
- 默认不写入 `.devbox` 之外的业务数据；不修改用户 Shell 配置，不执行管理员权限操作。

## 开放决策与风险

| 主题 | 当前决策 | 后续触发条件 |
| --- | --- | --- |
| Git 系统安装 | 当前版本只检测，不自动接管系统 Git | 明确 Homebrew、winget、apt 与提权模型后单独设计 |
| Python 来源 | 优先由托管 uv 安装，DevBox 统一展示 | uv 无法覆盖的解释器或版本需求出现时增加独立 Provider |
| 第三方插件 | 首个版本只支持编译期第一方插件 | 出现真实外部扩展需求后设计独立进程或 WASM 沙箱 |
| DevBox 自更新 | 独立于工具安装链路 | 应用签名、发布链和回滚策略稳定后单独实现 |
| Windows arm64 | 仅在上游资产和原生验证都存在时开放 | 官方 uv 资产和 Tauri 运行时完成验证 |
| Windows 原子替换与文件锁 | 依赖操作系统独占锁和安全的替换/重试策略 | 实现阶段用真实 Windows 原生路径验证 |
| 长路径与杀毒软件占用 | 明确报错并保留原 active，不自动换目录 | 实际用户反馈或平台兼容性测试确认需要额外兼容层 |
| 结构化存储 | 使用版本化 JSON、原子写入和操作日志 | 多工具历史查询、统计或并发写入需求增长时迁移 SQLite |

## 后续演进

当前检测能力形成后，按以下顺序扩展：

1. Python 插件复用系统检测契约，并接入 uv 托管运行时的安装、验证和激活计划。
2. Node.js 插件验证归档安装、校验文件和双版本切换。
3. Git 检测与平台化安装策略，自动系统安装需另行审查权限边界。
4. 增加卸载、缓存设置、缓存清理和安装修复的完整命令与页面。
5. 完善代理认证、镜像、离线缓存和 Shell 集成的受控配置。
6. 操作历史和缓存规模增长后，再评估 SQLite 等结构化存储。
7. 在明确安全模型后增加独立进程或受限 WebAssembly 的第三方插件机制。
8. 单独设计 DevBox 应用更新器、签名验证和回滚，不与工具更新链路混用。

任何阶段都保持同一原则：插件负责工具规则，公共服务负责通用能力，Rust 持有权威状态，前端只组合展示与交互。
